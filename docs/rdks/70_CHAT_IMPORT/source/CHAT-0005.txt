Der går vist noget galt med vores vejrdata. blandt andet kommer alt vind fra open-meteo. Vores workflow i github kører også meget langt tid. Analyser dette grundigt og analyser for andre fejl og mangler. Gør klar til at lave rettelser.
Tænkte i 3m 18s
Jeg har gennemgået RavRadar(83), den aktuelle diagnostik og GitHub Actions-loggen samlet. Problemet er reelt, og det skyldes især en kombination af en fastlåst DMI-bulkproces, en uhensigtsmæssig faseopdeling og for aggressiv DMI-livefallback.
Hovedkonklusion
Den aktuelle kørsel gav:
Vind fra DMI: 4 af 231 zoner
Vind fra Open-Meteo: 227 af 231 zoner
DMI-bølger: 205 zoner
DMI-strøm og vandstand: 220 zoner
Kun 4 komplette DMI-zoner
Alle 231 zoner er markeret som fallback
DMI-livekaldet fik HTTP 429 efter ét forsøg
Det er altså ikke en generel DMI-nedetid. DMI-marine- og bølgedata findes i stor udstrækning. Det er specifikt vinddelen af DMI-bulkcachen, der er kollapset.
1. Den direkte årsag til Open-Meteo-vind
Workflowets DMI-bulkjob starter med samlingen:
harmonie_dini_sf
Det er netop DMI-modellen, der leverer vind.
Loggen viser:
[DMI bulk + 27.3s] harmonie_dini_sf:
behandler forecast-step 1/17
Derefter kommer der ingen yderligere status i næsten 14 minutter, hvorefter GitHub dræber processen:
The action 'Update DMI bulk model cache' has timed out after 14 minutes.
Resultatet er, at den nye vindcache aldrig færdiggøres eller checkpointes. RavRadar beholder derfor den tidligere cache, som kun indeholder DMI-vind for fire zoner.
Den tidligere diagnostik viser, at systemet få timer før havde:
DMI-vind: 231 af 231 zoner
Den nye kørsel reducerede det til:
DMI-vind: 4 af 231 zoner
Det dokumenterer, at vindmodellen tidligere virkede. Fejlen er opstået i den nuværende bulkbehandling eller dens cachetilstand – ikke fordi DMI mangler vinddata.
2. Hvorfor bulkjobbet hænger
Tidsgrænsen i Python-scriptet ser umiddelbart korrekt ud:
maksimal intern runtime: 660 sekunder
reserve til afslutning: 120 sekunder
effektiv arbejdsperiode: 540 sekunder
Men tidskontrollen foretages kun mellem GRIB-meddelelser:
while True:
if should_stop_work():
interrupted = True
break
gid = codes_grib_new_from_file(handle)
Når scriptet er inde i:
nearest_valid_batch(...)
nearest_candidates(...)
codes_grib_find_nearest(...)
codes_get_elements(...)
kan det ikke afbrydes.
For hver relevant GRIB-meddelelse udføres der potentielt:
231 zoner
cirka 33 probe-positioner pr. zone
op til fire gridpunkter pr. probe
tusindvis af ecCodes-opslag
Det giver omtrent:
231 × 33 = 7.623 codes_grib_find_nearest-kald
for blot ét grid, før cachen er fuldt opbygget.
Hvis grid-signaturen ændrer sig mellem GRIB-meddelelser, eller cache-genbrug ikke rammer, gentages det. Derfor kan én enkelt forecast-step blokere hele Python-processen længere end dens interne deadline.
GitHub kan afbryde selve processen, men Python-scriptet får ikke mulighed for at:
gemme sidste checkpoint
skrive outputs
gemme vinddata
opdatere collection state
rydde den rå cache ordentligt
3. Faseopdelingen forværrer problemet
update-weather.mjs gør dette:
const marineCacheCompleteAtStart =
activeZoneIds.every(zoneId =>
recordHasMarine(nextDmiForecastStore.zones?.[zoneId], generatedAt)
);
const acquisitionPhase = marineCacheCompleteAtStart
? 'dmi-wind-wave-enrichment'
: 'dmi-marine-cache-warmup';
Det betyder, at DMI-vind kun hentes via live-EDR, hvis samtlige aktive zoner først har komplette marinedata.
Hvis blot én zone mangler vandstand eller strøm, bliver fasen:
dmi-marine-cache-warmup
og så kaldes DMI sådan:
fromDmi(feature, generatedAt, {
includeAtmosphere: false
})
Vind bliver dermed bevidst fravalgt.
Det er en uhensigtsmæssig kobling:
manglende strøm i én kystzone bør ikke blokere DMI-vind for resten af Danmark
DMI-vind og DMI-marine bør have uafhængige reparationskøer
systemet bør aldrig kræve 100 % marinekomplethed, før vind må opdateres
Dette er en af de vigtigste arkitekturfejl.
4. HTTP 429 stopper for meget
Efter bulkjobbet fejler, forsøger den centrale vejropdatering live-DMI.
Den første zone får:
DMI: HTTP 429
Derefter stopper resten af DMI-livekøen.
Samtidig springes DMI-vandstandsobservationerne over:
skipReason: skipped-after-http-429
Problemet er, at én 429 fra ForecastEDR også blokerer OceanObs. Det er to forskellige datatyper og muligvis forskellige API-belastninger.
Konsekvensen bliver:
ingen live-DMI-vind
ingen live-DMI-marinereparation
ingen nye vandstandsobservationer
næsten alt afhænger af den gamle cache
Cooldown bør opdeles i mindst:
ForecastEDR atmosphere
ForecastEDR marine
OceanObs stationer
OceanObs observationer
STAC/bulk-download
En fejl i én kanal bør ikke stoppe de andre.

Rettelserne bør gennemføres i denne rækkefølge
Kritisk rettelse 1: Gør bulkprocessen reelt afbrydelig
GRIB-behandlingen skal flyttes til en separat workerproces pr. asset eller forecast-step.
Så kan hovedprocessen:
sætte en reel timeout
terminere en hængende ecCodes-worker
gemme checkpoint
fortsætte ved næste kørsel
markere præcis hvilket asset der hænger
Python-tråde er ikke tilstrækkelige, fordi et blokerende C-kald i ecCodes ikke nødvendigvis kan afbrydes sikkert.
Kritisk rettelse 2: Del marine, vind og bølger op
Collection-køerne bør være uafhængige:
marine-reparation
vind-reparation
bølge-reparation
Vind må ikke vente på 100 % marinekomplethed.
Kritisk rettelse 3: Beskyt cache mod komponenttab
Ved merge skal hvert timestamp og hver komponent bevares individuelt:
wind
wave
current
waterLevel
waterTemperature
Ny cache må kun erstatte en eksisterende komponent, når den nye værdi:
er gyldig
har nyere model-reference eller generationstid
har tilstrækkelig horisont
består plausibilitetskontrollen
Kritisk rettelse 4: Kør ikke tung vindbulk hvert 10. minut
HARMONIE-vind behøver ikke fuld GRIB-genbehandling ved hver vejropdatering.
Et bedre mønster er:
let vejropdatering hvert 10.–30. minut
OceanObs cirka hver time
ny HARMONIE-bulk kun ved nyt model-run
marine/bølge-bulk kun ved nyt model-run
målrettet komponentreparation mellem modelkørsler
Kritisk rettelse 5: Separate rate-limit-domæner
En 429 fra ForecastEDR må ikke blokere OceanObs eller STAC.
Forbedring 6: Reducer Open-Meteo-kald
Brug deduplikerede koordinater og ét samlet forecastkald pr. geografisk punkt.
Forbedring 7: Sammenhængende diagnostik
Alle diagnostikfiler bør få:
{
"pipelineRunId": "...",
"deployedVersion": "4.0.x",
"conditionsGeneratedAt": "...",
"bulkCacheGeneratedAt": "...",
"forecastStoreGeneratedAt": "..."
}
Eksportværktøjet bør advare om mismatch.
